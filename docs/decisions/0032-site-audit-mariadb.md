# 0032: ログイン・配信履歴を専用MariaDBへ非同期保存する

- 状態: 採用
- 日付: 2026-09-16

## 背景

ユーザーはログインと配信の記録を残すよう依頼し、0ypで使用中のMariaDBを利用できると説明した。0ypを参照したテーブル設計後、実装の指示を受けた。

## 決定

- 0ypとは別DB・別ユーザーにaudit_events / broadcasts / broadcast_inputsを置く。スキーマは版・checksum付きの明示移行とし、実行時にDDL権限を要求しない。
- 0ypの原記録とセッション集約の分離、明示カラム、database/sqlとmysqlドライバーを採用する。miはライフサイクルの発生点で通知し、UTCで保存する。
- SQL・ファイルI/Oを配信・認証の経路で待たない。上限付きメモリーキュー、永続JSONL、単一writerで送信する。DB障害で配信を止めない代わりに、満杯・未同期データの消失は許容し、通常ログ・管理状態・audit.gapで表す。
- 各イベントは不変のIDを持ち、集約はrevisionで制御する。作成・受信開始・終了を区別し、旧bootの終了不明は検知時刻を別に残す。PCP ChannelIDを再利用しても履歴は分ける。
- 旧RTMP接続に結び付いた配信インスタンスが既に置き換わっている場合、その切断で新しい枠を停止しない。設計で合意した枠単位の終了記録と一致させる。
- 管理者と所有者を区別するため、サイト管理経路は許可ID・Origin・CSRFの検証後に同一プロセス内のJSON-RPCハンドラーへ渡す。ADR 0024のloopback HTTP中継を、この構成ではcontextによる身元引き継ぎに変更する。公開API・認証条件は維持し、身元指定ヘッダーは導入しない。
- 既存のキー・フォーム履歴JSONは維持する。JSON履歴保存失敗による枠取消も維持し、create失敗を1回記録する。
- 初期段階はSQL参照と管理者限定の状態API。保持期間は既定90日。一般ユーザー向けの履歴APIは作らない。

## 設計案から確定した実装上の選択

記録・ライフサイクルは `internal/audit`、SQLは同パッケージの `mysql.go` に分離する。1ファイル32MiBの追記ではなく、最大256件のバッチをsync後にrenameする。取込位置はメモリーに保持し、再起動時はファイル単位で再送する。書込途中・DBタイムアウトからの復帰を単純化し、原イベントの重複排除で再送を安全にする。

期限切れライフサイクルは原記録を復活させず集約だけを照合に使う。欠落検出は保守的とし、開始より先に集約が届いた場合もincompleteを保持する。完全な無欠落証明には使用しない。

## 却下した案

- ファイルだけの保存: 日時・アカウントでの検索と集計が扱いづらい。
- SQLite: 利用可能なMariaDBと0ypの運用経験を使えるため、別のDB運用を増やさない。
- 同期INSERT: DB障害で認証やメディアを遅らせる。
- 0ypのテーブル・JST・ポーリングの流用: YP掲載とmiの配信枠・実受信区間は意味が異なる。
- audit_eventsのみ: 区間や配信単位の照会が複雑になる。
- キーやフォーム設定もDBへ移行: 今回の記録保存より動作変更が大きく、DB停止時の配信継続を難しくする。
- サイト管理者をHTTPヘッダーで渡す: 外部入力と内部の身元情報を分けるための署名・トークン管理を増やす。同一プロセスのハンドラーを利用する。
