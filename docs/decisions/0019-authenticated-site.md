# 0019: 公開 PCP を維持し、サイト利用だけ X 認証で制御する

- 状態: 採用
- 日付: 2026-09-14

## 背景

ユーザーは peca-live の視聴体験と X ログインを希望した。目的は映像の限定公開ではなく、自サイトの帯域を無条件で利用させないこと。公開 PCP 中継を制限する要求ではないと明示され、その後実装を依頼された。[調査記録](../reviews/2026-09-14-peca-live-viewing-auth-design.md) を参照。

## 決定

- `internal/site` に利用者用 HTTP サーバーを追加し、Go プロセス内で Manager を利用する。管理 JSON-RPC を汎用プロキシとして公開しない。`site.enabled` の既定は false とし、従来のノード運用は維持する。
- サイト有効時はノードの `/stream/` と `/pls/` を起動時生成の内部トークンで保護する。サイトだけがこのトークンを使い、公開 PCP `/channel/` と ping は従来どおり。localhost の HTTP 視聴も例外にしない。ADR 0016 の公開 HTTP 方針に対する、明示的なサイト有効モードの例外である。
- X OAuth 2.0 Authorization Code + PKCE S256 を直接使う。X の本人情報 API が返す ID を識別子とし、ログイン成功者にサイト視聴・本人の配信操作を許可する。承認制・X 認証バッジ判定は設けない。
- セッションと OAuth フローはメモリー内に保持する。再起動は全ログアウト。トークンをブラウザーへ渡さず、X の access token も本人確認後は保存しない。Web セッションは固定 12 時間で、期限切れ・ログアウト時に該当メディア接続を終了する。
- 永続的な配信キー所有者は既存のキー保存で `site:x:<X ID>` に対応付ける。表示名では識別しない。キーはサーバーで暗号学的乱数を生成する。1 ユーザー 1 キー・同時 1 配信枠。停止とキー再発行は分離し、配信枠がある間は再発行を拒否する。
- サイトの同時視聴数は全体 20 / ユーザー 2 を既定とし設定可能にする。別セッションでも同一 X ID の利用枠を共有する。既存ノードの帯域・視聴上限も重ねて適用する。
- 最初の視聴対象は自ノードに登録済みのチャンネル。任意 `tip` や管理操作を利用者から受け取らない。外部 YP 一覧・掲示板・お気に入り同期・HLS 等は後続作業に分ける。
  - 同日の追加依頼により、外部 YP 一覧とカタログ経由の中継開始を [ADR 0021](0021-yp-channel-directory.md) で追加した。
- キー保存は発行・失効のスナップショットと書込を同じロックで直列化する。発行の保存失敗時は以前のマッピングを維持する。他アカウントが使用する同じキーは登録を拒否する。公開利用者の追加に伴い、所有権の一意性と発行成功の意味を保つため。

## 却下した案

- **映像自体を非公開 / PCP を制限**: ユーザー要求と異なる。
- **UI のログインだけ追加**: 映像 URL 直打ちでサイト帯域を消費できる。
- **localhost なら HTTP 視聴は無認証**: 無制限リバースプロキシの設定で迂回を作りやすい。
- **公開 UI から管理 JSON-RPC を呼ぶ**: 他人の配信キー取得やノード停止を許す危険がある。
- **別 Rails / Firebase サービスを必須にする**: 今回の最小機能には不要で、デプロイ要素が増える。peca-live の画面設計は参考にするが認証コードは転載しない。
- **X token / セッションの永続保存、refresh token の取得**: 長期 API 操作をしないため初期実装では不要。再起動時の再ログインを受け入れる。
- **キーをハッシュだけで保存する変更**: 現行キー一覧・ChannelID 生成・管理 API への影響が大きい。既存 0600 の生値保存を維持し、UI 伏字・ログ除去・管理 API 分離で扱う。管理者はキーを取得できる。

## 結果・影響

サイトは HTTPS の同一オリジンで UI / API / 映像を公開する。Go 側のサイト HTTP 入口は既定 loopback で、HTTPS 終端は外部プロキシが担当する。RTMPS を使う場合は TLS 終端も別途必要で、Go RTMP サーバー自体に RTMPS を追加したわけではない。

2026-09-14 追記: 当初は公開配信入力に TLS 終端を設ける方針だったが、ユーザーが OBS から公開 RTMP とストリームキー認証で接続するよう指定した。yayaue.me では `rtmp://yayaue.me/live` を直接公開する。RTMPS と SSH トンネルは採用しない。既存の発行済みキー検証を使い、サイトの HTTPS・X 認証は維持する。

サイト有効時、従来の `/pls/` を直接開く外部プレイヤーや管理 UI の直接視聴リンクは利用できない。サイトを利用するか、別の公開 PCP ノードで視聴する。サイト無効時は従来どおり。

ログアウトは Web セッション・その視聴を終了するだけで配信キーは無効化しない。OBS 等の配信はキー保有で認証される。アカウント停止・承認制・既存 RTMP 接続の強制切断は今回追加しない。
